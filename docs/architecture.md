# 统一部署约定

前端和后端仍是独立仓库。部署仓库不修改业务源码，运行时复用两端真实配置加载器、迁移器及节点管理服务。
当前兼容基线为 backend `b463ba542db010eb902d097be8947aa96c942afd`、frontend `44462ee`；实际构建从所选源码目录读取锁文件，并记录两端 commit 和工作树是否有改动。

## 配置所有权

`config.yaml` 的 `deployment` 管路径和启动方式，`backend`、`frontend` 分别保留原部署 YAML 的完整结构。
不将统一 YAML 直接交给应用。运行目录下生成两个兼容文档，每个子进程明确指定自己的 `CONFIG_FILE` 和数据路径。
前端 YAML 环境不注入 Node 的全局环境，防止阻碍浏览器配置热读取和复现 ESM/CommonJS 令牌丢失问题。

`var/runtime/baseline.yaml` 保存上次与统一配置同步的运行文档。每次打开/保存执行三方合并，接纳浏览器修改；同字段并发修改报冲突。
所有含凭据的文档使用同目录临时文件、0600 权限和原子替换。保存有配置锁，运行文档写入遵循前端 `config.yaml.switch.lock` 协议。
备份统一配置时保留 `.bak`；不记录明文凭据到普通日志。

## 构建与切换

源码目录是 Git 工作树，构建结果与运行状态放在部署配置旁的 `var/`。
backend 使用白名单目录生成代码快照，frontend 使用原有宿主/插件分离流程编译。源码树不会被构建污染。
成功后才更新 `var/built.yaml`；旧运行服务在整个编译阶段仍可使用旧快照。
Docker 前端单独编译复用最后成功构建记录的镜像与后端快照。临时编译容器共用 worker 数、内存上限、网络与 npm 缓存设置。宿主及插件均编译成功才更新构建记录。新版本通过 `start` 切换，原容器的绑定挂载随其生命周期固定。

启动先检查产物、镜像和部署方式，再停止本实例、检查数据库和迁移、配对，再从即将启动的后端产物登记插件清单并启动；准备失败保持停止并保留旧产物，不假设数据库可自动回滚。
准备阶段与服务进程共用数据目录锁，以免把其他运行版本的插件清单替换掉。登记复用后端命令，幂等发布设置，保留插件启停及业务数据。

已初始化数据库的迁移只由显式命令执行；只对经过 pg_catalog 检查的空库允许初始化。
配对使用后端现有节点管理服务（含锁、审计和同步队列），不直接拼 SQL 更改注册表。
首次自动登记节点、开启节点并读取真实 source_epoch；前端已有 UUID 与目标数据库不同则停止，防止误接数据库。
调用来源仍校验真实 socket IP 与节点令牌；统一部署新增回环来源，保留已有手动来源列表。

## 进程管理

Docker 中 `--init` 配合 Python supervisor；直接部署中用户级 systemd 管理同一 supervisor。
supervisor 为 API、Celery worker、Scheduler 和 Node 分别创建进程组；任一意外退出都停止所有组，并返回非零。
SIGTERM/SIGINT 提供 35 秒退出时间，再清理残留子进程。数据目录的排他锁阻止同实例重复启动 Scheduler。
容器重启按校验归属后的完整容器 ID 执行，并检查两端就绪。容器/systemd 重启只执行 serve；清单登记、Git、npm、配对和数据库 DDL 都有各自的部署入口。

两端各自一个监听端口，前端网页与接收器共用该端口。统一部署内部使用回环 URL，对外发布 URL 独立配置。
宿主机反代信任网关按选定 Docker 网络解析，不能将内部调用的整个 CIDR 白名单等同于 HTTPS 代理信任。

## 当前边界

这是单机部署工具，不是多机滚动发布系统。不会自动切换数据库、搬迁数据目录、清理旧产物、重置 Git、修复合并冲突或管理 PostgreSQL/Redis 服务。
Docker 与原生编译产物不混用；切换部署方式必须重新构建。
现有源码仓库已有的单端 setup 仍可独立使用；迁移到统一部署后，不再同时用两个旧 setup 管理同一实例。
